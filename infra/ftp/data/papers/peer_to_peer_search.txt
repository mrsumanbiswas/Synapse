Sharding a Search Index Across Peers Without a Coordinator
Authors: Daniel Okafor, Priya Nair and Tomas Varga
Contact: priya.nair@synapse-demo.example.org
Published: 2025
Note: sample document written for the Synapse demo corpus; the references are real.

Abstract
We describe a small peer-to-peer search system in which every participant runs an identical node holding one
shard of the index. Documents are placed with rendezvous hashing, queries are broadcast to all peers in parallel
and merged by score, and global statistics are recomputed by whichever peer leads a rebuild. We relate the design
to distributed hash tables, consistent hashing and large-scale data processing systems.

Keywords: peer-to-peer, sharding, consistent hashing, distributed search

1 Placement
Chord maps keys onto a ring of nodes and finds the owner of any key in a logarithmic number of hops [1]. Consistent
hashing, introduced for web caching, guarantees that adding a node moves only a small fraction of keys [2], and
rendezvous (highest-random-weight) hashing achieves the same property without a ring by picking the node with
the largest hash of node and key [3]. Dynamo combines consistent hashing with replication to stay available when
nodes fail [4].

2 Query processing
Broadcasting a query to every shard and merging the partial top-k lists mirrors the map and reduce phases of
MapReduce [5]. Shards must agree on term statistics, otherwise scores from different nodes are not comparable; a
leader collects document frequencies, computes global weights and broadcasts them [5, 6]. Ordering such updates
needs a notion of time across machines, which logical clocks provide [7].

3 Discussion
Without replication a failed peer makes its shard unavailable; the remaining peers still answer [1-4]. Storage
systems such as the Google File System show how replication can be layered on later [6].
